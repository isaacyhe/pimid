================================================================================
EXECUTIVE SUMMARY
================================================================================

The PIMID simulator implements a sophisticated, modular plugin system that 
allows developers to extend core functionality without modifying the codebase.

Key Findings:
- 8 plugin types defined (2 fully implemented, 6 framework-ready)
- Central PluginRegistry using singleton pattern
- Dynamic loading via dlopen/dlsym
- Configuration-driven via YAML files
- Base interfaces for extensibility

================================================================================
THE 4 PRIMARY PLUGIN TYPES (AS REQUESTED)
================================================================================

1. CORE MODELS (PE_TYPE)
   - Location: plugin_interface.h (enum)
   - Purpose: Custom Processing Element architectures
   - Status: Framework ready, awaiting implementations
   - Use Cases: Custom accelerators, heterogeneous PEs

2. SCHEDULERS (SCHEDULER)
   - Location: pimid/include/plugin/scheduler_plugin.h
   - Purpose: Task scheduling algorithms for PEs
   - Status: Fully implemented with 3 example plugins
   - Existing: DataLocalityScheduler, EnergyAwareScheduler, CustomScheduler
   - Features: Data locality, load awareness, priority, dynamic adaptation

3. MEMORY MODELS (MEMORY_MODEL)
   - Location: pimid/include/plugin/memory_model_plugin.h
   - Purpose: Memory technology implementations
   - Status: Fully implemented with 6 memory models
   - Existing: DRAM, SRAM, STT-MRAM, ReRAM, PCM, generic NVM
   - Features: Latency, bandwidth, power modeling, atomic ops

4. NETWORK MODELS (NETWORK_TOPOLOGY)
   - Location: pimid/network_models/include/network_model.h
   - Purpose: Network-on-chip topologies and routing
   - Status: Fully implemented with GARNET integration
   - Supported: MESH, TORUS, FAT_TREE, DRAGONFLY, H_TREE, CROSSBAR
   - Features: Multiple routing algorithms, energy modeling, VC support

================================================================================
PLUGIN REGISTRATION MECHANISM
================================================================================

Three-Phase Process:

Phase 1: Plugin Creation
  - Inherit from appropriate base class
  - Implement virtual methods
  - Create metadata
  - Provide factory function

Phase 2: Registration
  - extern "C" void pimid_register_plugin() function
  - Register with PluginRegistry
  - Called via dlsym() during library loading

Phase 3: Usage
  - Configuration specified in pimid_config.yaml
  - PluginRegistry::createPlugin(name, config)
  - Plugin instance available for simulation

Dynamic Loading Flow:
  Config → PluginRegistry::discoverPlugins() → dlopen() →
  dlsym(pimid_register_plugin) → call registration function →
  Plugin self-registers → Ready for instantiation

QUICK EXAMPLE: CREATING A PLUGIN
================================================================================

1. Header (my_scheduler.h):
   #include "plugin/scheduler_plugin.h"
   
   class MyScheduler : public pimid::plugin::SchedulerPluginBase {
       bool initialize(...) override;
       void shutdown() override;
       std::unique_ptr<PEScheduler> createScheduler(...) override;
       // ... other methods
   };

2. Implementation + Registration (my_scheduler.cpp):
   extern "C" {
       void pimid_register_plugin() {
           PluginRegistry::getInstance().registerPlugin(
               "MyScheduler", registration);
       }
   }

3. Configuration (pimid_config.yaml):
   plugins:
     loaded_plugins:
       - name: "MyScheduler"
         library: "plugins/libmy_scheduler.so"
         config: {...}

4. Build:
   mkdir build && cd build
   cmake .. && make && make install

================================================================================
KEY DESIGN PATTERNS
================================================================================

1. Registry Pattern
   - Central PluginRegistry manages all plugins
   - Singleton for global access
   - Type-safe plugin creation

2. Factory Pattern
   - PluginCreateFunc for plugin instantiation
   - Decouples creation from usage

3. Configuration Validation Pattern
   - validateConfig() for early error detection
   - getRequiredParameters() for documentation
   - getParameterDescriptions() for help text

4. Dynamic Loading Pattern
   - dlopen/dlsym for runtime loading
   - pimid_register_plugin() entry point
   - Self-registration mechanism

5. Template Method Pattern
   - PluginBase provides common functionality
   - Type-specific base classes (SchedulerPluginBase, etc.)
   - Subclasses implement specific behavior

================================================================================
IMPORTANT NOTES
================================================================================

1. Fully Implemented Types: SCHEDULER, MEMORY_MODEL, NETWORK_TOPOLOGY
   These have complete interfaces and example implementations.

2. Framework Ready Types: POWER_MODEL, PE_TYPE, ADDRESS_MAPPER, 
   CACHE_REPLACEMENT, PREFETCHER
   These are defined in the enum but lack detailed interfaces/implementations.

3. Registration is Key: Every plugin MUST have extern "C" pimid_register_plugin()
   This is called by PluginRegistry::loadDynamicPlugin() via dlsym.

4. Configuration Driven: Plugins are specified in pimid_config.yaml, making
   them easy to enable/disable without code changes.

5. Extensible Design: Adding new plugin types requires:
   - New enum value in PluginType
   - New interface class (optional but recommended)
   - New base class for convenience (optional)
   - Documentation update
